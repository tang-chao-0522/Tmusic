# TMusic 需求与接口 Review 记录

> Review 对象：PRD v0.1、API Contract v0.1  
> Review 日期：2026-10-03  
> 结论：**有条件通过，可进入 UI/技术方案评审；P0 决策完成前不建议正式开发播放源和认证模块。**

## 1. Review 摘要

当前文档已覆盖用户要求的 React 前端、Node.js + MongoDB + Redis + WebSocket 后端、网易云播放源、个人歌单、评论、一起听实时交流、AI 悬浮球/对话页，以及未来 Agent + RAG 自动选歌与创建歌单。

参考项目定位已核对：只有 Music Claw 是网易云方向；Spotify Clone 和 Jammify 分别采用自有上传/Cloudinary 与 JioSaavn 等来源。Review 中只把它们作为实时社交、社区、搜索和交互设计参考。

方案的核心边界合理：

- 网易云通过 Provider Adapter 接入，TMusic 业务模型不依赖第三方响应字段。
- 一起听同步的是“控制状态与播放时钟”，而不是由服务端转发音频。
- 活跃房间状态放 Redis，永久业务数据放 MongoDB，职责清晰。
- AI 首期提供完整 UI 与流式接口骨架；未来通过受限工具调用扩展，不让 Agent 直接写数据库。
- 房间即时聊天与内容评论是两套模型，避免生命周期、权限和查询方式相互污染。

## 2. 阻断项（P0）

以下问题需要产品负责人/项目所有者决策：

| ID | 问题 | 风险 | 建议 |
| --- | --- | --- | --- |
| P0-01 | 当前已确定仅供个人学习，但网易云接口仍可能变化或受条款限制 | 播放能力可能失效，公开部署会扩大风险 | 保持本地自用；不得实现绕过会员、登录或地区限制，未来公开前重新评估 |
| P0-02 | MVP 登录方式未确定 | 影响用户表、认证接口、UI 与通知通道 | 默认采用邮箱/用户名 + 密码；若优先国内用户，可在 P1 增加手机验证码 |
| P0-03 | Music Claw 将网易云 Cookie 存在 localStorage 并通过查询参数传递 | XSS、访问日志或代理可能泄漏账号会话 | TMusic 已建议只做扫码绑定，凭据服务端加密保存，前端不可读 |
| P0-04 | 数据保留与删除策略未定 | 聊天、评论、AI 对话涉及隐私和治理 | 明确保留期、用户删除、举报证据和审计数据的例外规则 |

## 3. 高优先级改进项（P1）

| ID | 发现 | 文档当前处理 | 实施建议 |
| --- | --- | --- | --- |
| P1-01 | 房主断线与多端登录可能引发脑裂 | 定义 30 秒宽限和权威版本 | 以 `roomId` 分布式锁/原子脚本选主；同一用户多连接只认当前控制设备 |
| P1-02 | 临时播放 URL 到期会造成成员不同步 | 定义 resolve 与一次刷新 | 房间切歌前各端预取；以 `room:ready` 汇总准备度，设置最大等待后开始 |
| P1-03 | 外部歌曲元数据会变化或消失 | 使用 TrackRef 快照 | 歌单项保留最小展示快照，同时按 TTL 刷新 availability，不保存临时 URL |
| P1-04 | 评论计数并发下可能漂移 | 允许冗余计数并提出校正 | 唯一索引 + 事务/可靠事件；增加每日校正任务和指标 |
| P1-05 | AI 对话可能越权读取用户偏好 | 定义 `allowTasteProfile` | 授权应由服务端用户设置控制，不能只信请求参数；工具每次复核 scope |
| P1-06 | REST 快照和 WS 连接之间存在竞态 | 快照含一次性 ticket，WS 再发快照 | 客户端以 WS 的 `room:snapshot` 为最终事实；REST 快照仅用于首屏 |
| P1-07 | 大歌单完整排序开销高 | 文档保留两种选项 | MVP 可先用完整 item ID 数组并限制 500 首；超过后改 LexoRank/位置操作 |
| P1-08 | 搜索/播放第三方故障会放大 | 已要求超时、熔断与缓存 | Provider 定义错误分类、超时预算和降级返回；按来源分开熔断 |
| P1-09 | AI 流式事件恢复需要缓存 | 已定义 Last-Event-ID | 保存有限事件序列；完成后以持久化消息作为最终结果，断流可重新查询 |
| P1-10 | WebSocket 鉴权状态可能在连接期间变化 | 只定义握手鉴权 | 定期复核 session/ban/mute，权限变化即时推送并撤销对应能力 |

## 4. PRD Review

### 4.1 完整性

通过。核心用户、范围、优先级、流程、数据职责、性能、安全、合规、验收和里程碑均已覆盖。

需要 UI 稿后补充：

- 桌面/移动信息架构和响应式断点。
- 播放器 Dock、全屏播放、房间聊天、评论树、AI 面板的组件状态图。
- 空态、加载、错误、网络断开、不可播放、权限不足等异常视觉。
- AI 球的尺寸、安全区、遮挡规则与 reduce-motion 动画参数。

### 4.2 范围控制

通过。MVP 已将推荐算法、好友系统、公开主题房和完整 Agent/RAG 延后，避免首版同时承担内容平台、社交网络和智能体平台三种复杂度。

建议坚守的切分顺序：

1. 先完成单人播放内核与 Provider 稳定性。
2. 再在同一播放内核上接房间同步，禁止另写一套房间播放器。
3. 评论与 AI 壳可并行，但 Agent 写操作必须晚于歌单接口稳定。

### 4.3 可验收性

基本通过。PRD 已给出关键指标和四组端到端场景。进入迭代前还需把指标映射到自动化测试：

- Audio Engine 单元测试：队列、循环、URL 刷新、错误跳过。
- 两到五个浏览器实例的房间同步测试：延迟、乱序、丢包和重连。
- 评论幂等与并发点赞测试。
- AI SSE 断开恢复、取消和草稿发布幂等测试。

## 5. API Review

### 5.1 一致性

通过。资源路径使用复数名词，动作型接口仅用于 `refresh`、`resolve`、`publish`、`cancel` 等无法自然表达的命令。时间、ID、游标、错误和响应信封有统一约定。

确认过的边界：

- 搜索、歌词与播放地址属于 Catalog/Playback，不与用户歌单混合。
- REST 管理房间资源，WebSocket 管理实时状态。
- 评论使用统一 target 模型；歌曲由 `provider + sourceId` 标识。
- AI 消息创建返回 Run，SSE 只传流式事件，最终消息仍持久化可查询。

### 5.2 鉴权与权限

有条件通过。接口已定义 Cookie/Bearer、CSRF、短期 WS ticket、资源权限与管理员审计。实施时必须补一份路由级策略代码，不能仅依赖控制器内零散判断。

建议权限声明形式：

```ts
policy("room.playback.control", ({ user, room }) =>
  room.ownerId === user.id || room.coHostIds.includes(user.id)
);
```

禁止以客户端传来的 `role`、`allowTasteProfile`、`ownerId` 作为授权事实。

### 5.3 实时一致性

通过设计评审。`stateVersion`、`queueVersion`、`commandId`、服务端时间、ACK、快照恢复构成了最小可用的一致性协议。

实施时需要固定三个原则：

1. Redis 中的房间状态只能通过原子操作更新。
2. 客户端只应用更高版本，不用本地事件时间覆盖服务端状态。
3. 音频加载失败只影响该客户端，不反向暂停整个房间；房主可看到成员未就绪状态。

### 5.4 可演进性

通过。Provider、AIProvider、Agent 工具和 TrackRef 均设置了隔离层，后续更换音乐来源、模型或拆分服务不需要修改前端核心实体。

## 8. Review 决策建议

建议本轮评审采用以下默认决策，若无异议即可作为 v0.2 输入：

- 前端：React + TypeScript + Vite，TanStack Query，Zustand，Howler.js，Socket.IO Client。
- 后端：Node.js + TypeScript，NestJS（Fastify adapter）或直接 Fastify 二选一；优先团队熟悉度。
- 实时：Socket.IO + Redis Adapter；AI 流式使用 SSE。
- 数据：MongoDB 持久化，Redis 承担缓存/限流/在线状态/房间权威状态。
- 控制权：MVP 默认房主独占，可授权协作者；普通成员可申请点歌。
- 评论：TMusic 自有评论和网易云只读评论采用双 Tab、独立游标，不伪装同源。
- 房间消息：房主可选持久或临时；临时消息在房间结束/最后成员退出时删除。
- AI：首期只做会话和结构化卡片，P1 做歌单草稿，所有发布操作由用户确认。
- 部署：模块化单体起步，不在 MVP 预先拆微服务。
